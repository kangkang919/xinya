#### F9 完整出题与调度逻辑

**一、题目来源（4 个触发点）：**

| 触发时机 | 代码位置 | 行为 |
|---|---|---|
| 新建心得时 | `entries/route.ts` → `preGenerateQuestions` | 异步调 DeepSeek 生成 1 道题 + AI 摘要，创建 QuizQuestion + QuizRecord（answeredAt=null, nextReviewAt=明天） |
| 编辑心得时 | `entries/[id]/route.ts` → `regenerate` | 删除旧题（保留有答题历史的），重新生成 1 道新题 |
| 定时重生（F9.22） | `daily-backfill.ts` → `runRegenerate` | 每周三/六凌晨 3:00，为已答对过的心得从不同角度生成新题 |
| 兜底补全（F9.21） | `daily-backfill.ts` → `runBackfill` | 每周三/六凌晨 3:00，为完全没有题目的心得补生成 |

**二、每天弹什么题（调度器 `getTodayCard`，按优先级从高到低）：**

| 优先级 | 条件 | 行为 |
|---|---|---|
| 0 | `lastCardDate === 今天` | 返回 null（今天已弹过，不重复） |
| 1 | `nextReviewAt ≤ 现在`（到期题） | 排序：答错优先 > 久未复习优先；取前 10 个随机选 1 道 |
| 2 | `answeredAt = null`（从未答过） | 按 nextReviewAt 升序，取前 10 个随机选 1 道 |
| 3 | 心得完全没有题目 | 返回心得信息，前端触发在线生成 |
| 4 | 以上都没有 | 找 nextReviewAt 最早的（最久未复习），取前 10 个随机选 1 道 |

**三、答题后调度更新（`submitAnswer`）：**

| 结果 | streak 变化 | nextReviewAt 计算 |
|---|---|---|
| 答对 | streak + 1 | 现在 + 2^streak 天（1→2→4→8→16…间隔递增） |
| 答错 | streak 归零 | 现在 + 1 天（明天再复习） |

**四、定时重生流程（F9.22）：**

1. 查找所有有答对记录（correct=true）的心得
2. 为每篇心得调 DeepSeek 从不同角度生成 1 道新题（传入旧题内容避免重复）
3. 旧题的所有 QuizRecord → nextReviewAt 设为 100 年后（退休，不再弹出）
4. 新题创建 QuizQuestion + QuizRecord（answeredAt=null, nextReviewAt=明天, streak=0）
5. 邮件通知管理员重生结果

### 2.6 系统提示词设计（如涉及 LLM）

#### 角色 1: 心芽拾遗出题老师（已实现）

> 见 `lib/deepseek.ts` 的 `generateQuestions`：以老师角色对单篇心得出 3 道题（单选/多选/判断），同时生成 ≤150 字要点总结（keyPoints）。

#### 角色 2: 心芽洞察分析师（已实现，F5.9）

> 见 `lib/deepseek.ts` 的 `generateMonthlyInsight`。输入源为当月全部心得的 AI 总结（keyPoints），月末结算后生成月度成长洞察。

```
你是“心芽”里的洞察分析师，一位温柔、诗意、从不评判的成长陪伴者。
基于用户某月全部心得的要点总结，凝出一枚月度成长洞察，只返回 JSON：
{
  "themes": ["主题关键词2-4个，每个≤4字"],
  "moodTrend": "整体情绪基调与变化（1-2句，温柔观察，不说教）",
  "growth": "内心的成长或探索（1-2句，肯定式的发现）",
  "encouragement": "一句诗意的鼓励（≤30字，像朋友写在叶脉上的话）"
}
语气：温柔、克制、诗意，多用自然意象（叶、光、根、季节），不列举数字，不喊鸡汤口号，不发散。
```

**生成规则（F5.9）：**
- 触发：仅已结束的自然月（北京时间跨入次月 00:00:00 后该月才结算），当前月显示“进行中”
- 门槛：当月非草稿心得 ≥ 3 篇才生成，不足 3 篇显示温柔提示
- 缓存：每月每用户一条，存于 `InsightReport`（type=monthly，唯一约束 userId+type+periodStart），永久不重复生成；生成失败不缓存可重试
- 输入：优先用各心得 keyPoints，缺失时用标题+正文前 50 字兜底

## 附录 A-0：开发约束与问题诊断规范（必读）

### 规则 1：开发前必须核对本文档

每次新建开发需求时，**必须先读取本文档**，逐条核对：
- 新需求是否与已确认功能冲突
- 改动是否会影响已有功能（特别是路由、中间件、配置文件、环境变量）
- 有冲突的必须经过用户确认是否继续
- 开发完成后**必须同步更新**本文档的变更记录（附录 A）

### 规则 2：问题诊断第一原则

发现 bug 时，第一步必须判断问题来源：

| 问题类型 | 判断标准 | 排查方式 |
|---------|---------|---------|
| **历史遗留** | 功能一直有问题，今天才发现 | 按问题现象直接排查修复 |
| **迭代引入** | 之前正常，某次改动后出问题 | **必须回溯 git 历史 diff 对比** |

### 规则 3：迭代问题的标准排查流程

```
1. git log --oneline --since="YYYY-MM-DD"  → 找到时间范围内的所有commit
2. 确定最后正常工作的commit（用户确认或测试验证）
3. git diff <正常版本>..<当前版本> -- <关键文件>  → 精确对比差异
4. 重点关注：新增文件、路由文件、配置文件、环境变量变更
5. 不要盲目添加修复代码，先理解"什么改动导致了问题"
```

### 规则 4：Next.js 路由优先级警示

- `app/page.tsx` 优先级高于 `app/(group)/page.tsx`
- **禁止**在 `app/page.tsx` 中使用无条件 `redirect()`，会覆盖路由组
- 未登录跳转逻辑应放在 middleware 中处理，不在页面组件中

### 规则 5：禁止盲目叠加修复

- 不确定根因时，不要同时改多个文件
- 每次修改只改一个地方，验证后再改下一个
- 修改前先问自己："这个改动是否可能引入新问题？"

### 规则 6：部署时必须主动提供服务器部署指令

每次代码变更完成、需要用户部署时，**必须在回复中主动附上完整的服务器部署指令**，不要等用户来问。

### 规则 7：时区一致性——所有日期判断必须使用北京时间

**事故背景（2026-07-25）：** 拾遗功能使用 `new Date().toISOString().split("T")[0]` 计算“今天”，返回的是 UTC 日期。北京时间 07:00 对应 UTC 前一天 23:00，导致：
- 学习画像按 UTC 日期统计，今早答题被计入昨天
- 卡片弹出判断“今天”=UTC日期，与 lastCardDate 相同，误判今日已弹过卡片

**强制规范：**
1. 任何涉及“今天”“某天”的日期字符串计算，**必须使用 `beijingDateString(new Date())`**（位于 lib/utils.ts）
2. 禁止在业务逻辑中直接使用 `toISOString().split("T")[0]` 作为日期判断
3. 数据库存储的 DateTime 为 UTC，前端展示和统计时必须转换为北京时间
4. 新增日期相关功能时，必须验证“北京时间 00:00~08:00 时段”的跨天场景

### 规则 8：数据删除安全——禁止无差别删除用户历史数据

**事故背景（2026-07-27）：** 执行“批量重生成题目”脚本时，无差别删除了所有旧 QuizRecord（含已答过的 answeredAt/correct/streak），导致学习画像数据永久丢失（531条→374条，4条已答记录被删）。

**强制规范：**
1. **删除操作必须区分“未使用”和“已使用”数据**：删除旧记录时，必须加 `answeredAt: null` 等条件过滤，保留有用户行为历史的记录
2. **批量操作前必须备份**：任何批量删除/更新脚本执行前，先 `pg_dump` 备份
3. **外键关联删除需先检查依赖**：删除父记录前，先查询是否有子记录引用，有则保留父记录
4. **脚本必须输出删除摘要**：打印“删除 N 条，保留 M 条”，便于事后审计

**通用原则（适用于任何项目）：**
- 用户产生的数据（答题记录、操作日志、交易流水等）属于“不可再生数据”，删除前必须确认是否可恢复
- “重新生成”类操作的正确模式：先创建新数据，再删除旧的未使用数据，而非“先全删再重建”
- 数据库删除操作必须有 WHERE 条件约束，禁止无条件 DELETE

### 规则 9：数据库 Schema 变更安全（prisma db push 禁令）

**事故背景（2026-07-24）：** 本地执行 `prisma db push` 同步 schema（仅修改 Tag 表），导致服务器 QuizRecord 表 529 条答题记录全部被重置为初始状态，数据不可逆丢失。

**强制规范：**
1. **严禁使用 `prisma db push`**：必须使用 `prisma migrate dev --name xxx` 生成明确 SQL 迁移文件
2. **操作前必须备份**：`pg_dump -U xinya xinya_db > /tmp/backup_$(date +%Y%m%d_%H%M).sql`
3. **迁移后必须验证**：检查关键表数据量（`SELECT count(*) FROM "QuizRecord" WHERE "answeredAt" IS NOT NULL`）
4. **生产环境部署流程**：备份 → 审查迁移SQL → 执行迁移 → 验证数据 → 部署代码

### 规则 10：配置审计清单——Code Review 之外必须单独执行

**背景（2026-07-29）：** 两次全面 Code Review 均未发现双项目的密钥隐患（萌宠 JWT 公开默认值、本项目 `doc/.env.production.备份` 曾进公开仓库历史提交）。根因：Code Review 只审查“当前源码快照”一个维度，而敏感配置风险横跨四个维度，必须联合对账才能判定。

**四维对账表**：每一项密钥/凭证都必须逐行回答以下四个问题，任何一格答不上来即为审计不通过：

| 密钥项 | ①源码怎么读它 | ②本地 .env 配了没 | ③服务器 .env.production 配了没 | ④进过 Git 历史没 |
|---|---|---|---|---|
| `JWT_SECRET`（JWT 签名） | 仅环境变量，缺失即 throw（lib/auth.ts） | 必须有 | 必须有 | 不得出现 |
| `DATABASE_URL`（含数据库密码） | 仅环境变量（Prisma） | 必须有（隔 SSH 隧道） | 必须有 | 不得出现 |
| SMTP 授权码 | 仅环境变量（lib/mailer.ts） | 可选 | 必须有 | 不得出现 |
| `DEEPSEEK_API_KEY` | 仅环境变量（lib/deepseek.ts） | 可选 | 必须有 | 不得出现 |
| （新增密钥时在此表加行） | — | — | — | — |

**硬规则**：
1. 签名/凭证类密钥**一律不得在代码中设默认值**；缺失时必须显式失败（拒绝启动/throw），禁止静默退回任何硬编码值。启动失败是显式可见的故障，静默降级是无声的安全事故。
2. 依赖“打印警告让人去看”的安全提示视为无效机制——警告会淹没在日志里，必须改为强制机制。
3. 第④维用 `git log --all --name-only -- "*.env*"` 核查历史提交，不能只看当前工作区（当前干净≠历史干净）；一旦发现历史泄露，处置方式是**轮换密钥**，而非仅删除文件（历史提交中仍可被任何人翻出）。

**触发时机**（三选一命中即执行全表对账）：
- 新增任何密钥/凭证配置时
- 部署到新环境（新服务器/换电脑）时
- 每次 Code Review 时**额外单独跑一遍**（Code Review 本身覆盖不了②③④维）

### 规则 11：文档单一事实来源与身份牌维护规范

**背景（2026-07-31）：** 文档全面整理时发现 5 处文档间冲突（三份换电脑文档互相打架、v2.0 与本文档同时自称权威、富文本规范与代码相反等）。根因：同一事实被复制到多份文档，更新时只改了一处，其余副本逐渐腐化成“看上去可信的错误信息”。

**硬规则**：
1. **一个事实只住一个家**，其他文档只放链接不复制内容。归属表：
   | 信息类型 | 唯一归属文档 |
   |---|---|
   | 功能/约束/技术栈/变更记录 | 本文档（新芽 dev-framework.md） |
   | 密钥/账号/服务器门禁 | 双项目密钥凭证地图.md |
   | 环境搭建/迁移/部署流程 | 心芽换电脑迁移指南.md |
   | 文档导航 | 心芽项目资料索引.md |
   | guest 账号清单 | 邀请码.md |
2. **每份文档头部必须有身份牌**（状态 🟢活文档/🟡经验存档/⚫历史存档 + 权威来源 + 最后核对日期）；新建文档时同步加上。
3. **过时文档移入 doc/archive/ 并加作废注，不直接删除**；经验类文档放 doc/经验/，定位为不随代码更新的存档。
4. **交付时同步**：开发完成除更新本文档外，若改动涉及密钥/环境/迁移流程，必须同步更新对应归属文档（已列入附录 C 交付清单）。
5. **新建文档前先查归属表**：若主题已有归属文档，在既有文档内更新，禁止另起新文档造成第二份副本；确需新建时，同步在资料索引文档地图登记。
